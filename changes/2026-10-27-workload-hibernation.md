## Delta

**An idle workload costs its flavor until something stops it, and a stopped one costs a cold start to come back.** The only runner is the [k8s-runner](../architecture/k8s-runner.md): one Pod per workload, alive at full allocation from the first inbox item until the class's `idle_timeout` (default five minutes) stops it, then gone — processes, shells, scratch space and all — until the next item pays for a Pod again. Pod startup is measured at around eleven seconds; `runtimeClassName: kata-fc` adds a VM boundary but changes neither number, because the VM belongs to Kata's shim and nothing in the platform can pause it. An agent that answers a message every few hours therefore either idles at full cost between turns or cold-starts for every one of them, and nothing in between exists: no Runner RPC, no workload status, no record field, no decision in the Orchestrator knows a workload that is neither running nor stopped.

|---|---|

### Boundaries

Hibernation is something a runner advertises and the Orchestrator decides. The k8s-runner advertises nothing and keeps its behaviour to the letter; an environment on it sees no change. The Orchestrator decides because only it can see that an inbox is empty, which is the one fact that makes a pause safe; the runner persists and restores and never reasons about work.

The workload spec is unchanged. The k8s-microvm-runner consumes what the Orchestrator assembles today — containers, sidecars, init containers, volumes, inline files, pull credential, flavor name — and realizes it inside a guest. Nothing about what a workload contains, how MCP sidecars are reached, how the Ziti sidecar enrolls or how egress is policed is redefined.

### What does not change

The idle timeout, the activity sweep, the Start Decision's retry policy, volume reconciliation and TTL, identity orphan reconciliation and the metering sampler all keep their shape; each gains the hibernated case rather than a parallel mechanism. Pull credentials stay per workload and short-lived. Exposed ports and egress rules hang off the identity and survive sleep with it.

## Acceptance Signal

On a k8s-microvm-runner, an agent instance that has just answered a message shows a workload that goes `running → hibernating → hibernated` within seconds of the turn's ack, emits no `FLAVOR_SECONDS` records while asleep and emits `resource=snapshot` storage instead; the next message produces a reply from the **same** workload record — `hibernated → waking → running`, no new `starting` record — and the time from the message's `accepted_at` to the agent's first LLM call is a small fraction of a cold start on the same hardware, on the order of a second. A sandbox left unattended past its idle timeout shows `hibernated`, and `connect` returns to the same shells with their processes still running.

A hibernated workload stopped by `hibernation_ttl` leaves its volumes in place and the next message cold-starts on them, as any stop does today. On a k8s-runner, an agent's workload list is indistinguishable from before this change.

## Notes

Validated on 2026-10-27 in a nested-KVM k3s VM, first with Firecracker 1.17 and then with the design as specified — Cloud Hypervisor v52.0, virtiofsd 1.14.0 and the Kata 4.3.1 guest kernel, image and agent, driven without the shim from a prototype runner enrolled on the platform and running as an unprivileged k3s Pod with a device plugin. On Cloud Hypervisor the real agent pod (three init containers and `agynd` on a shared volume) starts in 55 s cold including image unpack, 22 s with images cached, of which 14 s is the guest booting to its agent; pause 3–5 ms; the first memory snapshot of a 2 GiB guest takes 80–200 ms and occupies 85–200 MB on disk, because guest memory is a shared memory file with free-page reporting and the snapshot is sparse; a wake restores and resumes in 200 ms and has the guest agent answering at 290–340 ms, after which `SIGCONT` reaches the container's init and its handler runs; a hibernation after an on-demand wake writes only the pages touched since (20 ms, merged into the previous snapshot in 80 ms). Under nested virtualization every first touch of a page after a wake is a fault of about a millisecond; production hardware must be measured before the wake budget in the acceptance signal is committed to. On 2026-10-28 the round trip ran through the platform in the local bundle, with the prototype enrolled as a runner and an agent whose environment names it: a chat message made the Orchestrator start the workload it assembles today — init containers, Ziti enrollment, sidecar and readiness waits, `agynd` and the agent runtime — and the reply came back through the LLM proxy; the workload was then hibernated from the runner's side (pause 10 ms, snapshot 1.3 s, 461 MB), a second message was sent while it slept, and after the wake (restore and resume 454 ms, agent reachable at 350 ms) the answer arrived 2.8 s after the message. Start to running took six minutes in the nested VM, four of them in the gateway readiness wait while the sidecar's first calls to the Ziti controller timed out; what that costs on real hardware is part of the node check.

Decisions taken: Cloud Hypervisor rather than Firecracker, after the Firecracker prototype showed that a snapshot cannot include vhost-user devices, which left the guest's filesystems as block devices inside the guest and every snapshot as large as the flavor's memory — Cloud Hypervisor's virtio-fs share puts a workload's writes on the slot's disk, its sparse memory snapshots cost what the guest holds rather than what it was given, and the Kata guest boots on it with the agent as PID 1, with no kernel of the platform's own; the storage model of [agent-substrate](https://github.com/agent-substrate/substrate) — a stock Kata guest on virtio-pmem with DAX, one virtio-fs share, host-side overlays, `find-paths` restore — adopted as it stands, but the platform's own slot supervisor rather than substrate's worker and control plane; slots as Pods rather than a privileged node daemon, so that the scheduler accounts for every guest. Cloud Hypervisor is pinned at v52: v53 prefaults every page of an on-demand restore in the background, which makes the next snapshot full-sized again (measured: 2 GiB and 9 s instead of 85 MB and 100 ms); the pin moves when a release makes the prefault optional. Cloud Hypervisor v53 also advances the guest clock across a restore by itself; until then the supervisor's clock set after resume is what corrects it. The image proxy is reached by the hostname in the reference, as a node reaches it today: the deployment is responsible for that name resolving from a Pod, and the runner carries at most a CA bundle for it — not the runner-side host-to-service mapping the prototype used, and not an address in the workload spec, which the Orchestrator would then have to know per cluster. Slots live in the workload namespace rather than one of their own, which would only duplicate its policy. The runner is built in a repository of its own, `agynio/k8s-microvm-runner`: what the two runners share — enrollment with the Gateway, catalog reporting, the Runner API server, state reporting and the metering sampler — is extracted from the k8s-runner into a module both import, rather than the k8s-microvm-runner becoming a second backend inside the k8s-runner, whose every release would then carry it.

Three install surfaces follow the runner rather than precede it: the workload NetworkPolicy template needs egress to the image proxy and the snapshot store; the proxy's hostname must resolve from a Pod, which in the local bundle it does not — there it names the node's own loopback, so the bundle adds a cluster DNS rewrite to its ingress, as it has for the console name, and hands the runner its CA; and the bundle's image bake fills the node's container store, which this runner does not read — the bundle either extends the bake to the runner's cache or accepts a first-use pull through the proxy, and its disk, sized for a platform that keeps no workload state, grows to hold slot caches and snapshots. The slot Pod's security context is the one found necessary in the prototype and recorded in the spec: an unconfined AppArmor profile, because the runtime's default profile denies `mount`; `SYS_ADMIN` for the share's mounts; `SYS_PTRACE` for userfaultfd (or the node sysctl); `DAC_READ_SEARCH` and `SETPCAP` for virtiofsd. The runner is brought up in the local bundle first; to verify on production nodes after that, and before the wake budget in the acceptance signal is committed: KVM on the Magnum node image; that the Pod Security configuration of the workload namespace admits that security context, or that user namespaces are available to confine it; userfault-driven page population from the object store; the object store the runner is given.

Depends on [runner-reported workload state](2026-08-11-runner-reported-workload-state.md): a hibernation is complete when the runner says so, and a wake is a transition the chat indicator follows within a second, not a reconcile interval. Sequenced in three steps after it, each leaving the platform working: the Runner API and the Runners and Orchestrator surfaces first, with the k8s-runner unaffected and nothing yet advertising `hibernate`; then the extraction of the shared runner front from the k8s-runner, and the k8s-microvm-runner on it with cold boot, hibernate and wake, whose snapshots are already incremental; then templates. Server-side enrollment of the workload's OpenZiti identity — handing the guest an enrolled certificate instead of a JWT — would take the remaining second out of a template start and is a change of its own.
